# 五分钟演示与面试讲解

本演示使用 `backend/tests/test_db.py` 的合成数据：2026-09-01 至 09-07 支付金额 1000 元，退款发生额 100 元，期间收支差 900 元。它只用于验证功能和口径，不代表真实店铺业绩。四类运营工作流的端到端验收（含多来源 26 题与 11 个运营场景）另见 [Task 11 日期化发布验收](superpowers/research/2026-09-14-task-11-release-acceptance.md)；那份报告同时列出了本轮**未执行**的外部验证（真实 provider、真实接口取证、生产部署与恢复、一周试用）。

## 演示步骤

1. 按 [运行手册](runbook.md) 启动 FastAPI 与 Vite，打开 `http://127.0.0.1:5173`。
2. 新建对话，问“最近7天支付金额如何？”。助手通过 `query_business` 返回脱敏聚合结果和覆盖范围。
3. 继续问“那上个月呢？”。会话保留店铺和指标，但覆盖不足时返回缺数据，不能把局部日期当整月。
4. 问“9月1日至7日退款发生多少？”。结果为 100 元，包含跨期退款，不把它称为利润。
5. 问“假设下月销售10万元，推广费率12%”。助手通过 `evaluate_promotion` 返回 12000 元上限，并标注该数值来自用户假设。
6. 问“最近7天实际推广费率和 ROAS”。助手说明快麦数据尚未证实推广实耗，不能计算。

## 模块边界

| 模块 | 输入 | 输出 | 责任 |
| --- | --- | --- | --- |
| React 工作台 | 会话与 SSE | 聊天、状态、附件 | 会话操作和展示，不存密钥 |
| FastAPI | 同源 HTTP 请求 | CRUD、SSE | 身份、Origin、会话并发边界 |
| Agent | 用户问题、历史 | 六个受限工具调用（一次完整业务请求通常一次业务 Tool） | 路由、参数补全、澄清、匿名映射、预算与降级 |
| 指标 | 参数化查询 | Decimal 聚合结果 | 覆盖、权限、金额和指标口径 |
| 同步 | 快麦分页响应 | 经营事实和水位 | 幂等、回滚、拆合单与退款处理 |

可用 provider 由 `LLM_PROVIDER=qwen|deepseek` 在 API 启动时确定。离线验收验证协议和业务结果；真实 provider 尚需单独在合成库完成 smoke 和修订后的 26 题后才能记录为已测（旧 20 题只是合并回归基线）。四类运营工作流的当前状态：商品运营与平台 / 店铺对比已可在已对账平台上展示（其余平台永远保留能力缺口标签）；上架价复核与库存预警在真实部署里只会报「来源尚未取证」，不报价格差异也不报库存安全——演示时要说清这一点，不得拿合成用例的通过冒充线上可用。

## 五分钟演示步骤（四工作流）

1. 商品运营：「直钉枪在所有店铺近七天卖得怎么样？」——一次工具调用拿到跨店表与七日趋势；商品文字命中多个候选时要反问，不代选。
2. 平台对比：「五个平台近七天哪个卖得好？」——表格与柱图逐项相等；缺数的平台只给原因，不给 0 柱子，合计与排名只覆盖同口径分组。
3. 单店下钻：「比较一下抖音各店铺的支付金额」——点一个平台只发一句新请求，窗口与口径沿用本轮，范围由服务端重新展开授权。
4. 价格复核：「直钉枪的标价是 19.90，都对不对？」——目标价只认本轮这句；下一句不给价就只反问不沿用。当前无真实渠道在售价来源，它会如实回答「来源尚未取证」。
5. 库存预警：「看一下全商品总库存和店铺预警」——实物与渠道可售两行各说各的：三店共仓 100 件仍只有 100，缺阈值是「未配置」而不是「安全」。当前无真实库存来源，同样只报「来源尚未取证」。

## 真实模型验收基线（2026-09-11，首次执行；已退役为历史基线）

> **2026-09-14 状态：** 本节用的是旧 20 题题库，只能作为历史基线。题库已扩到修订后的 26 题，
> 真实 provider 的 smoke 与 26 题 live **尚未重跑**（本轮不接触模型凭证），因此本节数字
> 不得引用为多来源或四工作流的真实模型验收结果。

此前 `docs/metrics.md` 与运行手册都把真实模型联调标为"未实测"。本节是第一次执行结果。

- 模型：`deepseek / deepseek-v4-flash`（唯一 provider，无自动切换）
- 数据：**独立合成验收库** `bi_agent_acceptance`（本机实例内新建，按 001→009 初始化），
  题库为 `backend/tests/questions.jsonl` 的 20 题
- 结果：**通过 14 / 20**，平均单题 3.6 秒，最慢 13.3 秒；`--offline` 仍为 20/20

失败分类（逐条查证，不统一归给"模型不行"）：

| 题 | 现象 | 查证结论 |
| --- | --- | --- |
| 07 / 12 / 20 | 期望 `metrics=['paid_amount']`，实际多带了 `aov`/`paid_orders`/`refund_amount` | 数据与金额正确；是题库断言**要求指标集合完全相等**。是否允许"多取指标"是口径决定，未擅自放宽断言 |
| 06 | 把"9月1日至7日比前7天"解析成 8/25–9/8 且 `compare=none` | **真实的模型日期推理缺陷**：窗口与比较方式都错，连带数值错（500 vs 1000） |
| 16 | 期望 `evaluate_promotion` 返回 `missing_data`，实际 `ok` | 单独调用该工具核实：确实返回 `missing_data` +「尚未取得推广实耗…只能做明确假设的预算测算」，**没有编造广告数据**。失败在模型的工具选择/路由 |
| 18 | `remaining_days` 期望 2、模型算 3 | 题库期望按 `end - spent_through` 计，模型按含首端计。属**未定义口径**，需先定规则再改断言 |

结论：本轮暴露的 6 项里没有一项是"金额算错"或"数据被编造"——确定性工具与门禁都按预期工作；
缺陷集中在模型的时间解析与工具路由，以及题库断言口径过窄。

### 执行方式与一个安全前提

`tests.acceptance --live` 会把 `seed_business_case` **写进 `BI_TEST_ADMIN_DSN` 指向的库**。
本仓库的 `bi_agent_test` 里存有真实同步数据，直接指过去会污染它，因此必须先建独立库：

```powershell
psql -d postgres -c "CREATE DATABASE bi_agent_acceptance"
# 按运行手册顺序对其执行 001 → 009
uv run --env-file ../.env.app python -m tests.acceptance --live
```

另需注意：`--live` 只从环境变量取模型配置。若沿用 `.env.test` 里的桩模型，它会以
`"model": "fake-model"` 静默跑完并报出 17 题失败——那不是产品结果。执行前必须确认
输出的 `model` 字段是真实型号。
