# 快麦可拉取数据复核

核查时间：2026-09-06，北京时间14:35—14:39。依据用户提供的 [llms.txt](https://open.kuaimai.com/llms.txt)、其链接的公开全文和现有账号只读抽样。

## 结论

**当前账号已取得订单/ERP出库、售后、商品与SKU当前成本、当前库存的真实样本；推广消耗仍未取得。** 历史成本、仓储销售出库单、销退入库和采购查询可以成功响应，但所选样本没有记录，不能当成已经具备完整可用数据。

本轮共25次只读请求，覆盖12种接口；其中16次初查、9次定向补查。没有修改ERP记录、刷新Token或尝试未发布方法。完整响应只在临时进程内处理，持久化结果只有平台分布、数量及字段覆盖统计，不含密钥、订单号、商品编码、店铺名称或客户信息。

主要业务样本按北京时间2026-09-05的修改时间获取，每个订单/出库请求只取一个店铺第一页20条；不是全天数据导出，也不能代表全公司日单量。库存是查询时点的快照；商品样本3个，SKU补查针对一个实际成交商品。销退、采购无记录后，补查范围扩大为2026-08-30至2026-09-05。

## 2. 推广费用再次核查

重新获取的官方索引及全文中，没有找到推广消耗、广告计划消耗、归因成交额或ROAS的公开查询方法；样本的订单及商品字段也没有明确广告消耗字段。

官方文档有两条明确边界：

1. 接入指南写明：“报表/智库模块的接口为增值接口，如果需要对接和使用，请联系销售同学或实施同学获取报价与接口文档。”
2. AI文本说明写明：“未发布接口、增值接口、内部接口、商家专属配置和非公开说明不会出现在 llms.txt 或 llms-full.txt 中。”

因此，目前结论是 **“公开方法与本次实测均未证实可取推广消耗”**，不能扩大成“快麦整个产品没有推广数据”。CLI介绍中出现“报表”一词，也不能证明这个账号能拉广告报表。

`discountFee`是优惠金额，`cost/purchasePrice`是商品成本，`postFee`是邮费/运费，采购`otherAmount`是其他费用；它们都不能直接映射为推广费。

推广模块的剩余前置条件：取得快麦实施提供的具体增值方法名和文档，确认该账号授权、店铺/日期/渠道粒度、币种、归因窗口、更新和回溯规则，再进行小样本验证。若快麦不提供，再选择广告平台导出CSV或授权API作为补充来源。

## 3. 对第一版数据设计的修正

### 可以进入接入与对账阶段

- **抖音经营查询**：先接普通订单、售后、店铺和商品，核对支付时间、拆合单及实付金额后，做期间概览、趋势、排行和退款分析。
- **淘宝/天猫ERP业绩**：交易出库已取到实付和成本样本，可做明确标注的ERP订单/出库口径分析；仍需状态范围、完整性与平台报表对账，不能仅因有数字就称其为完整平台支付GMV。
- **成本参考**：在订单及订单行保留源成本，商品表保留当前档案成本；订单已有成本，不必等待历史成本接口有数据才能展示ERP成本参考。历史成本仍是后续核验和重算来源。
- **当前库存**：库存状态和分仓数据可用，可作为商品经营查询的补充；它不是此次两个核心任务的必选模块，不因接口存在就扩建仓储系统。

### 仍需明确禁用或标注

- **拼多多完整销售指标**：普通订单接口不支持，出库样本缺支付金额/平台单号/修改时间，不能纳入全平台支付总额、客单价和费用率。当前只展示明确可用的ERP单据、数量或售后数据，并提示覆盖限制。
- **完整净利润**：实际运费缺失、理论运费部分为0、包材全0，其他平台扣费与推广费也未证实。ERP `grossProfit`只能称ERP毛利参考，不能视为净利润；0费用需先确认是否已维护。
- **历史库存**：当前库存接口不具备回溯时点证明。需要历史查询时，另行验证出入库流水覆盖或开始保存库存快照；不能把当前库存配上历史日期。
- **仓储出库明细、销退实收和采购支出**：文档支持，但样本为空，数据入口保留为条件项，暂不作为第一版必需依赖。
- **历史商品成本**：成功空结果必须标记“无记录”，不能自动用今天的档案成本替代所有历史成本。
- **真实投放复盘和ROAS**：推广实耗及归因收入仍缺，先保留明确输入假设下的预算测算。

### 实施时必须处理的接口差异

1. **空返回**：有的接口在 `success=true,total=0` 时省略 `list`；无列表且无`total`时只能标记“成功响应但未取得记录”。网络失败、业务错误、空结果分别处理，不能单凭缺列表判断无权限，也不能把非零`total`而无列表当空数据。
2. **金额单位**：订单买家实付、商品档案成本、售后退款文档多标注元；采购`totalAmount/actualTotalAmount`、采购明细`price/amount`明确标注分。按接口字段逐一转换，不能全局统一除100。
3. **成本粒度**：订单`cost`表示所有商品总成本；普通订单行`cost`文档说明需乘`num`才是该商品总成本；部分套件子结构又将`cost`标为总成本。按完整字段路径定义口径，避免对不同`cost`字段使用同一公式或把订单成本重复乘数量。此次仅做字段数值检查，尚未验证全部成本公式。
4. **标识映射**：交易明细使用`itemSysId/skuSysId`，商品/成本接口请求使用`sysItemId/sysSkuId`；应显式映射，不能只按名字相似自动转换。平台商品编码、ERP商品编码、SKU编码需分开。
5. **时间与增量**：订单使用`timeType=upd_time`及字符串日期；售后使用`startModified/endModified`；仓储出库使用`timeBegin/timeEnd`毫秒值，公开时间类型列表没有修改时间选项。不能给全部接口套一个更新时间同步器。
6. **平台缺字段**：拼多多样本没有`modified`，不能依赖其构建源记录版本；用成功窗口和完整快照处理当前可见字段，完整订单同步仍应使用获授权通道。
7. **分层校验**：先确认`success`/错误码，再检查响应形状、匹配总数及字段覆盖；数值需区分缺失、零、正数、负数和非法值。负毛利可能是正常业务结果，不应当成API错误。
