# 决策：放弃拼多多支付接入

日期：2026-09-12，北京时间。决定人：用户。原文：「拼多多授权太复杂，放弃接入拼多多」。

本记录只登记范围决定与它的口径后果，不新增接口取证，也不改变任何已核验数字。

## 1. 决定内容

1. **不再申请拼多多方舟（自研）appkey**，不再把「等快麦侧开通拼多多授权」当作任何任务的前置。
   `docs/superpowers/research/2026-09-11-production-deploy-and-sync.md` 与
   `2026-09-12-taoxi-onboarding.md` 中依赖该授权的待办就此关闭。
2. 多来源设计里 `pdd，方舟开通后` 那一行（第三个订单源、逐项实测支付口径）**从路线中删除**，
   保留为「不接入」而不是「延后」。
3. 拼多多店铺保留在店铺档案内，可继续走已核验的非敏感单据通道，因此
   `erp_documents`（ERP 单据数）在覆盖与质量成立时仍属可答能力。
4. 拼多多**永久不获得**支付类能力：`paid_amount`、`paid_orders`、`aov`、
   `product_paid_amount`、`cash_difference`、`cohort_refund_rate`。退款额、成本与毛利同样
   不在本次开放范围（实测该通道无支付金额，退款归属也未认证）。

## 2. 依据（既有实测，本轮未重跑）

- 2026-09-11 逐店取证：拼多多 0/13 店可用支付口径，实测 46/46 单单头与行级均无
  `payAmount`/`payment`，行 `oid` 也缺失（`docs/metrics.md` 第 6 节、
  `2026-09-11-production-deploy-and-sync.md`）。
- 用其他字段反推被屏蔽金额违反既有红线：「成功空结果 ≠ 无数据」，强行同步会把
  ¥0 收入冒充「确实没卖」。
- 方舟通道的代价是独立的平台侧授权、字段审批与敏感数据协议，收益只是补上 13 家店的
  支付口径；用户判断该代价不值得继续等待。

## 3. 对口径与验收的影响

| 位置 | 影响 |
| --- | --- |
| 来源注册表（设计 §3） | pdd 只剩 `erp_document/v1` 一行；支付依赖直接 `capability_unavailable`，不再出现「开通后」分支 |
| 全平台支付总额 | 分母不含拼多多，任何全平台汇总必须显式披露该排除范围（`excluded_scope`），不得把 13 家店算进覆盖 |
| Q22（拼多多题） | 保留，但预期从「方舟前不可用」改为「不接入：支付类永久不可用，单据数按覆盖可答」。它是 fail-closed 的负向断言，不需要任何拼多多授权即可测试 |
| 历史重放 / 回填 | 不为拼多多申请敏感通道；拼多多单据通道是否逐店开启仍按覆盖与质量取证，不因本决定自动开通 |
| 运营工作流计划目标范围 | 从「淘宝、拼多多、抖音、京东、快手」收缩为「淘宝/天猫、抖音、京东、快手、视频号、微购相册」；拼多多只在跨平台对比里作为缺失组出现 |

## 4. 保持不变的红线

- 未登记、未授权来源解析支付依赖时 fail closed，禁止回退交易源后把空响应标为完整覆盖。
- 不猜方法名、不用统一容差掩盖缺失字段、不把档案店铺数当同步完成数。
- 能力标签只能由证据（对账 + 版本化质量规则）授予，不因「同步成功」自动开通。
